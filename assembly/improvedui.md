# Improved UI — development plan (for AI agent delegation)

This document is the development plan for improving the embedded graphical interface of the
DAISY Pipeline 2. It is written so that it can be handed over as-is to an AI coding agent
(e.g. GLM 5.3): each section describes the context, the exact locations in the code, the data
formats, the expected features with acceptance criteria, and the conventions to follow.

# Context

This folder (`assembly/`) holds a java/maven project to package the "DAISY Pipeline 2" conversion
server. It also includes a command line interface and a swing-based graphical interface to use the
DAISY Pipeline 2 as a oneshot conversion tool to be launched from a terminal.
Currently, the graphical interface provided is only reporting progression of a conversion requested
from the command line.

# Codebase map (where to work)

All the code to modify lives in `assembly/src/main/java`:

- `GraphicalInterface.java` (default package) — the current Swing UI and the entry point launched
  by `pipeline2 ui` (see `assembly/src/main/resources/bin/pipeline2` and `pipeline2.bat`,
  `MODE=ui` sets `MAIN=GraphicalInterface`). Its `main(String[] args)` currently requires a first
  argument (a script name or a CLI command name); it delegates known commands to
  `CommandLineInterface.Command.fromName(...)`, otherwise opens a single progress window and runs
  the conversion through `startAsyncTask(script, options)` (a `SwingWorker` monitoring
  `SimpleAPI.startJob(...)` via `api.CommandLineJob`: `getStatus()`, `isProgressUpdated()`,
  `getUpdatedProgress()`, `getNewMessagesQueueItem()`, `getLogFile()`).
- `CommandLineInterface.java` (default package) — CLI with extra commands `descriptors`, `scripts`,
  `script --id <id>`, `datatypes`, `datatype --id <id>`, `settable-properties`, `help`. These commands
  export the XML resource files (see below) through `api.SimpleAPI` and the writers in `xml/`.
- `api/SimpleAPI.java` — singleton (`SimpleAPI.getInstance()`) exposing `startJob(String script,
  Map<String,? extends Iterable<String>> options)`, `getScripts(boolean withDetails)`,
  `getScriptDetails(String id)`, `getDatatypes()`, `getDatatypeDetails(String id)`,
  `getSettableProperties()` and `setProperty(String name, String value)`. Unknown options passed to
  `startJob` are ignored with a warning (see `CommandLineJobParser.withArgument`).
- `api/CommandLineJob.java`, `api/CommandLineJobParser.java`, `api/MessageQueueItem.java` — job
  monitoring model already used by the UI.
- `xml/ScriptsXmlWriter.java`, `xml/ScriptXmlWriter.java`, `xml/DatatypesXmlWriter.java`,
  `xml/PropertiesXmlWriter.java`, `xml/PropertyXmlWriter.java`, `xml/XmlUtils.java` — produce the
  XML formats described below.
- `ui/LiveJLabel.java` — `JLabel` with `AccessibleRole.ALERT`, used for the progress label; changes
  are announced to screen readers via `AccessibleContext.ACCESSIBLE_NAME_PROPERTY` (see
  `GraphicalInterface.updateProgress`). The `ui` launcher mode enables the Java Access Bridge
  (`jabswitch /enable` in `pipeline2.bat`), so accessibility must be preserved in new UI code.

Reference XML resource files are committed in this folder and must be treated as read-only samples
(they are regenerated by the CLI commands, never edited by hand):

- `assembly/scripts.xml` — export of all scripts **with details** (`scripts` command /
  `SimpleAPI.getScripts(true)`): 41 `<script>` elements with `id`, `input-filesets`,
  `output-filesets`, `<nicename>`, `<description>`, `<version>`, `<homepage>`, `<input>`/`<output>`
  ports (`name`, `nicename`, `required`, `sequence`, `mediaType`, `desc`) and `<option>` elements
  (`name`, `nicename`, `required`, `type`, `mediaType`, `desc`, `ordered`, `sequence`, `default`,
  `role`). Observed `input-filesets` values: `daisy202`, `daisy3`, `docx`, `dtbook`, `epub2`,
  `epub3`, `html`, `nimas`, `obfl`, `pef`, `zedai`.
- `assembly/datatypes.xml` — export of all datatypes (`datatypes` command): `<datatype id=...>`
  containing either a `<choice>` with `<value>` + `<a:documentation>`, or a `<data type=...>` with
  an optional `<param name="pattern">` (regex the value must match).
- `assembly/properties.xml` — export of settable properties (`settable-properties` command):
  `<property name=... desc=... value=.../>` where `value` may be absent (unset) or a default
  (`true`/`false`, an integer like `-999`/`999`, or any string).

User data directory ("appdata" folder): the launchers set the `PIPELINE2_DATA` environment variable
(`%APPDATA%/DAISY Pipeline 2` on Windows in `pipeline2.bat`; `$PIPELINE2_HOME/data` by default on
Linux/macOS in `pipeline2`). Resolution order to implement in Java: system property
`org.daisy.pipeline.data` if set, then environment variable `PIPELINE2_DATA` if set, then
`%APPDATA%/DAISY Pipeline 2` on Windows, then `$XDG_DATA_HOME/DAISY Pipeline 2` (or
`~/.local/share/DAISY Pipeline 2`) on Linux, then `~/Library/Application Support/DAISY Pipeline 2`
on macOS. Create the folder if missing.

Build / run for development: `make -C assembly dev-launcher` produces
`assembly/target/dev-launcher/pipeline2`; run the GUI with
`assembly/target/dev-launcher/pipeline2 ui [script --opt value ...]` and the CLI with
`assembly/target/dev-launcher/pipeline2 cli <command>`. The `with-simple-api` maven profile
compiles `assembly/src/main/java` with **source/target 8** into `target/simple-api`, on a plain
classpath (no module system): new code must be Java 8 compatible and placed in the default package
(main classes) or in the existing `api`, `ui`, `xml` packages.

# Features wanted

I would like to complete the graphical interface with the following features or scenarios.

## F1 — Cached scripts and datatypes definitions

If they don't exist, a cached definition of scripts and datatypes should be stored in the user data
folder (i.e. `"%APPDATA%/DAISY Pipeline 2/scripts.xml"` and `"%APPDATA%/DAISY Pipeline 2/datatypes.xml"`).
Current export of those files is implemented in the command line interface for the `scripts` and
`datatypes` commands (see `CommandLineInterface.Command`), i.e. through `SimpleAPI.getScripts(true)`
and `SimpleAPI.getDatatypes()`.

Acceptance criteria:
- On startup, the UI loads `scripts.xml` and `datatypes.xml` from the user data folder if present;
  otherwise it computes them via `SimpleAPI` (same calls as the CLI commands) and writes them to the
  user data folder.
- The cache is recomputed when the user data folder files are missing or when settings are saved
  (see F2).

## F2 — Settings dialog

A new "Settings" dialog would allow to load, modify and store back settings in the user data folder
of the DAISY pipeline 2 (i.e. on Windows, in `"%APPDATA%/DAISY Pipeline 2/user-settings.xml"`):
- A list of most properties is defined in the `properties.xml` file along this markdown, but some are
  "hidden" and would need to be added manually while they are not formally exposed.
- By default, those settings values are textual (String), but there can be boolean (true/false) or
  integer (-999/999) values, to deduce from the properties. The correct type of input should be
  deduced from the default value provided if it exists (a `JCheckBox` for `true`/`false`, a numeric
  text field for integers, a text field otherwise).
- When saving back the settings:
  - The properties should be set accordingly (via `SimpleAPI.setProperty(name, value)`).
  - The cached definitions of scripts and datatypes should be recomputed before closing the settings
    dialog (a small label next to the save button should indicate to the user that the program is
    "Reenabling...").
- Among settings, i would like to allow the user to create "scripts default settings": in a
  "Scripts options" tab, the user should be able to select a script in a list, and then view and
  modify default conversion options for this script. Those options should then be saved in the
  settings (`user-settings.xml`) and reused when launching a conversion with the script (merged with
  the values entered in the conversion form, the form values taking precedence).

Acceptance criteria:
- `user-settings.xml` is created in the user data folder on first save, and reloaded on startup.
- Each property row shows name, description and current value, with a typed editor deduced from the
  default value.
- Saving applies the properties, recomputes the `scripts.xml`/`datatypes.xml` cache, and shows the
  "Reenabling..." status next to the save button until done.
- The "Scripts options" tab lists all scripts from the cached `scripts.xml`; selecting one shows its
  options (from the script details) with editable default values, persisted per script id.

## F3 — Merged "Conversion form" and "Progress dialog"

Given a script definition, a new "conversion form" should allow a user to configure the script input,
output and options. A "Convert" button would launch the conversion to be monitored, similarly as what
is done with the current progress dialog implemented in the `GraphicalInterface` class.

If possible, i'd like to keep a "single window" approach: instead of opening a new window, the current
progress dialog becomes a full fledged conversion form, and during execution the progress message and
progress bar are displayed on top of the form. A "Details" button expands the UI on the left to show
the log in the text area; clicking the button again hides back the text area and reduces the UI area.

The conversion form is built from the script details in the cached `scripts.xml`:
- the `<input>` ports (name, nicename, required, sequence, mediaType) as file pickers,
- the `<output>` ports as output file/folder pickers,
- the `<option>` elements as typed inputs: `type="boolean"` or a boolean default → checkbox;
  `type="integer"` or an integer default → numeric field; a `type` referencing a `<datatype>` in
  `datatypes.xml` with a `<choice>` → combo box of the documented values; otherwise a text field.
  The `default` attribute pre-fills the input; `required` options must be filled before "Convert"
  is enabled.

Acceptance criteria:
- Selecting a script updates the form in the same window (no new window).
- "Convert" starts the job through the existing `startAsyncTask` monitoring loop; the progress bar,
  live label and log area behave as today.
- The "Details" button toggles the log text area without opening a new window.

## F4 — Full GUI usage

The following scenarios are considered:

- If the `GraphicalInterface` main function is called without any argument:
  - The code should open a file selection window, where the user can either browse for a file or
    drag-and-drop a file he wants to convert, and the user can browse for an output folder where the
    result would be stored.
    - Authorized input files are zip, html, "ncc.html" (daisy2.02), opf file (daisy3 or unzipped
      epub), epub file, docx document, xml files and pdf.
    - If the file is a zip: check if it contains an opf and if so identify it as daisy3; check if it
      contains an ncc.html and if so identify it as daisy202.
    - If the file is an xml file: check if the file is a dtbook file (with a `<dtbook ...>` root
      node); check if the file is a zedai file (with a `<document ...>` root node).
    - When the window is opening, the code should also start to load and cache all available
      conversion scripts and datatypes (see F1).
    - The output folder is mandatory, and a warning should be displayed if the selected folder is
      not empty.
    - A "Cancel" button would close the application.
  - Based on the selected file, the window should update to expose the list of available "scripts"
    that can take as input the file. Filter scripts by name prefix:
    - docx → scripts starting with `word-to`
    - daisy202 → `daisy202-to`
    - daisy3 → `daisy3-to`
    - html (not ncc.html) → `html-to`
    - epub → `epub3-to`
    - zedai → `zedai-to`
    - dtbook → `dtbook-to`
    - pdf → `pdf-to`
    Cross-check with the `input-filesets` attribute of each script in `scripts.xml` when available
    (e.g. the `docx` fileset matches the `word-to-*` scripts). Note: no script currently declares a
    `pdf` input-fileset in `scripts.xml`; in that case show an explicit "no script available for this
    file" message instead of an empty list.
  - Depending on the selected script, the window should update to display the "conversion form"
    underneath the "scripts" list (see F3): the list of options to be set by the user to run the
    conversion script, and a "Convert" button to launch the conversion with the currently selected
    options values. This button is first invisible (next to the "Cancel" button) and displayed only
    when a script is selected.
- If the `GraphicalInterface` main function is called with the command `prepare` followed by a
  script and a `--source inputfile` (and optionally other options of the script):
  - Register `prepare` in the `GraphicalInterface.Command` enum and handle it in `main` before the
    fallback to script execution.
  - Open a window that displays an output folder selector (label, text field and browse button that
    opens a folder selector) and the "conversion form" (see F3) pre-filled with the provided
    `--source` and options.

# Development plan (suggested order for the agent)

1. **T1 — User data folder + XML cache (F1).** New helper (suggested: `ui/UserDataStore.java` or in
   the default package) resolving the user data folder and loading/saving `scripts.xml`,
   `datatypes.xml` (via `SimpleAPI.getScripts(true)` / `getDatatypes()` when missing), plus parsing
   helpers for the three XML formats. Wire it into `GraphicalInterface.main`.
2. **T2 — No-argument flow (F4).** File selection window with browse + drag-and-drop, output folder
   selector (mandatory, non-empty warning, "Cancel" closes the app), input file type detection
   (zip/opf/ncc.html, xml root element dtbook/zedai, extensions html/docx/epub/pdf), script list
   filtered by prefix/fileset, then the conversion form and the "Convert" button reusing the
   existing `startAsyncTask` monitoring.
3. **T3 — Single-window merged progress (F3).** Turn the progress dialog into the conversion form
   with progress on top and the toggleable "Details" log panel.
4. **T4 — `prepare` command (F4).** Add `Prepare("prepare")` to `GraphicalInterface.Command`, parse
   `--source`/options, open the same window pre-filled.
5. **T5 — Settings dialog (F2).** `user-settings.xml` load/save, typed editors from
   `properties.xml` defaults, `SimpleAPI.setProperty` on save, cache recomputation with the
   "Reenabling..." label, and the "Scripts options" tab persisting per-script default options that
   are applied (as defaults) when building the conversion form.

Each task should be delivered as a small, reviewable change compiling with
`make -C assembly dev-launcher` (or `mvn -Pwith-simple-api -s ../settings.xml package` inside
`assembly/`).

# Conventions and constraints

- Java 8 language level, Swing only, plain classpath (no JPMS). Main classes stay in the default
  package (`GraphicalInterface`, `CommandLineInterface`); helpers go in `api`, `ui` or `xml`.
- Keep the existing runtime patterns: `SwingWorker` for the job, `SwingUtilities.invokeLater` for UI
  updates, stdout/stderr redirected to the log area, `JOptionPane` on failure offering to open the
  conversion log (copied to `.txt`, opened via `Desktop` only when supported), window closes a few
  seconds after completion, exit codes 0 (success) / 1 (error) / 2 (cancelled). Options are passed as
  `Map<String, List<String>>` built from `--name value` argument pairs.
- Accessibility: use `ui.LiveJLabel` for status messages and fire
  `AccessibleContext.ACCESSIBLE_NAME_PROPERTY` on text changes; keep components focusable and
  labelled (`setLabelFor`). New controls must expose accessible names.
- UI labels: keep existing ones unchanged (e.g. "Annuler"); use English for new labels, consistent
  with the existing majority ("Conversion failed", ...).
- Do not edit the committed `assembly/scripts.xml`, `assembly/datatypes.xml`,
  `assembly/properties.xml` by hand: they are reference exports produced by the CLI commands.
- Do not touch the webservice/web UI (`webui/`, `clientlib/`) or the CLI behavior; only the embedded
  Swing UI in `assembly/src/main/java` changes.

# Verification

- Build: `make -C assembly dev-launcher` (compiles the `with-simple-api` profile, Java 8).
- Run GUI scenarios manually:
  - `assembly/target/dev-launcher/pipeline2 ui` → file selection window, file detection, script
    filtering, conversion form, Convert, Details toggle, Cancel.
  - `assembly/target/dev-launcher/pipeline2 ui prepare <script> --source <file> [--opt val ...]` →
    pre-filled form + output folder selector.
  - `assembly/target/dev-launcher/pipeline2 ui <script> --source <file> --result <dir>` → unchanged
    one-shot progress window behavior.
  - Settings dialog: edit/save properties, verify `user-settings.xml`, property application and
    cache recomputation; verify per-script default options are reused in the conversion form.
- Regenerate reference XML via CLI to compare formats:
  `assembly/target/dev-launcher/pipeline2 cli scripts --result /tmp` (and `datatypes`,
  `settable-properties`).
- There are no automated tests for the Swing UI (`assembly/src/test` only contains xspec tests), so
  verification is compile + manual scenario runs.
